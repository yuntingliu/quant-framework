# 投资组合约束功能开发方案

[English](13_PORTFOLIO_CONSTRAINTS_WORK_PLAN.md) | 简体中文

## 一、现在有什么

当前 `alphalab/sdk/v1/research.py` 中的 `optimize_portfolio(...)` 已支持五种组合优化方法：

| 方法 | 功能 |
| --- | --- |
| `equal_weight` | 等权配置 |
| `minimum_variance` | 最小方差 |
| `risk_parity` | 风险平价 |
| `hrp` | 层次风险平价 |
| `max_sharpe` | 最大夏普比率 |

现有优化器已支持**单票权重上限、目标总仓位、现金及换手率约束**，能够处理当前持仓和候选池外的退出资产，并记录历史样本、协方差修复、风险贡献、Solver 状态等诊断信息。

目前主要有两方面功能缺口：

| 功能缺口 | 具体问题 |
| --- | --- |
| 组合约束不完整 | 尚未支持行业/分组、相对基准偏离、风险预算三类约束 |
| 执行验证不完整 | 核心目前主要检查股票池、单票上限和总仓位，缺少新增约束的统一检查、失败解释和执行前复核 |

## 二、目标与要求

**项目目标：扩展现有投资组合优化器，使用户能够设置更完整的投资限制，系统据此生成满足约束的组合权重，并对优化和执行结果进行验证。**

### 1. 新增三类约束

| 约束 | 作用 | 示例 |
| --- | --- | --- |
| 行业/分组约束 | 限制某个行业或资产组的合计投资权重 | 科技行业权重 ≤30% |
| 基准偏离约束 | 控制组合相对于基准指数的配置差异 | 科技行业相对基准偏离 ≤5 个百分点 |
| 风险预算约束 | 控制资产或行业对组合总体风险的贡献 | 科技行业风险贡献 ≤40% |

### 2. 核心要求

1. **统一规则：** 三类约束采用统一的数据结构，明确限制值、计算口径、优先级、容差和版本。
2. **数据可靠：** 行业分类、基准权重和历史收益使用决策时点已知的信息，缺失数据按照预先声明的规则处理。
3. **求解准确：** 成功权重满足全部硬约束；求解失败时明确区分数据错误、约束不可行、协方差问题和 Solver 失败。
4. **交易前验证：** 优化目标权重和执行调整后的计划权重均通过核心检查，违规计划被拦截。
5. **结果可追溯：** 保留数据与约束版本、实际值、限制值、容差、松弛度和 Solver 诊断，支持独立复核。

所有约束调整及优化方法切换均需用户明确确认。现有持仓、退出资产、现金与换手率必须纳入计算。

## 三、具体需要做什么

整体流程为：

**约束配置与数据准备 → 投资组合优化 → 约束结果检查 → 交易前复核 → 结果记录与展示。**

### 1. 建立统一接口

定义三个公共对象，供数据层、优化器、执行核心和 API 使用：

| 对象 | 主要内容 |
| --- | --- |
| `PortfolioConstraintSet` | 约束类型、上下限、容差、决策日、规则版本 |
| `PortfolioConstraintData` | 股票行业映射、基准成分及权重、数据有效日期、数据版本 |
| `ConstraintCheck` | 约束 ID、实际值、限制值、容差、松弛度、是否通过及失败原因 |

`optimize_portfolio(...)` 增加 `constraints` 和 `constraint_data` 两个可选参数，保持现有 SDK 调用兼容。

### 2. 建立统一的约束计算机制

新增公共计算模块，统一计算：

- **分组权重：** 各行业或资产组合计占投资组合的比例。
- **基准偏离：** 组合权重与对应基准权重之间的差额。
- **风险贡献：** 基于协方差矩阵计算个股或分组承担的组合风险。
- **约束检查：** 比较实际值与限制值，计算容差、松弛度和通过状态。

优化器在求解过程中使用这些计算规则；核心在交易前根据实际权重重新调用检查函数，保证两处使用一致的计算口径。

### 3. 扩展五种优化方法

保留现有优化目标，将新增约束加入求解过程：

| 方法 | 实现方式 |
| --- | --- |
| 等权 | 生成等权目标，再进行受约束投影 |
| 最小方差 | 在 SLSQP 中加入三类约束 |
| 风险平价 | 在 SLSQP 中加入三类约束 |
| HRP | 计算 HRP 目标，再进行受约束投影 |
| 最大夏普 | 保留显式预期收益要求，在 SLSQP 中加入三类约束 |

受约束投影应尽可能保留原始目标权重，并记录投影后的实际结果。风险预算涉及非线性计算，需要检验求解稳定性和各方法的适用范围。

### 4. 完善验证和诊断链路

核心增加两个检查节点：

- **目标权重检查：** 接收优化器输出时，核验全部硬约束。
- **计划权重检查：** 流动性、现金及交易成本调整后，重新检查计划权重。

检查结果写入运行记录，并经 API 传递到风险服务和策略工作台。用户能够查看各项约束是否满足、失败发生在哪个环节，以及相关调整建议。

## 四、三个人如何分工

采用三个模块分工：**A 负责约束与数据，B 负责计算与优化，C 负责执行验证与系统集成。**

### 成员 A：约束体系与数据接口

**目标：建立统一的约束输入，使优化器获得完整、有效、可追溯的规则与市场数据。**

| 任务 | 具体工作 | 主要文件 |
| --- | --- | --- |
| A1. 定义公共对象 | 实现三个公共对象及行业、基准偏离、风险预算约束的字段；确定计算口径、容差、版本和错误格式 | 新建 `sdk/v1/constraints.py` |
| A2. 实现数据校验 | 检查证券代码、重复记录、行业缺失、基准权重、日期、版本及必需字段；制定缺失数据处理规则 | `constraints.py` |
| A3. 接入约束数据 | 复用现有 `industry/sector_code`；增加按决策日获取行业分类、基准成分及权重的适配器，输出标准化数据 | `dataio/rq_frames.py`、`dataio/` |
| A4. 完成接口与测试 | 导出公共类型，提供三人共用的三资产测试 fixture，覆盖合法输入、缺失数据、未来数据和无效版本 | `sdk/v1/__init__.py`、`test_portfolio_constraint_data.py` |

**交付成果：** `PortfolioConstraintSet`、`PortfolioConstraintData`、`ConstraintCheck`，数据适配器及输入校验测试。

**完成标准：** 给定约束配置和决策日，能够生成可直接用于优化与验证的标准化数据；异常输入能够返回明确错误。

### 成员 B：优化算法与求解器

**目标：将三类约束接入现有五种优化方法，生成合规权重并解释求解结果。**

| 任务 | 具体工作 | 主要文件 |
| --- | --- | --- |
| B1. 开发约束计算模块 | 实现分组权重、基准偏离、风险贡献及 `evaluate_constraints(...)`，统一生成 `ConstraintCheck` | 新建 `sdk/v1/constraint_math.py` |
| B2. 扩展优化入口 | 增加两个可选参数，接收 A 的公共对象，保持旧接口兼容 | `sdk/v1/research.py` |
| B3. 接入五种优化方法 | 扩展 `_solve_weights` 和 `_project_weights`，加入行业、基准偏离、风险预算约束，保留现有现金和换手率处理 | `research.py` |
| B4. 完善求解诊断 | 求解后逐项检查约束；扩展 `PortfolioOptimizationError`，记录不可行约束、协方差问题、Solver 状态及调整建议 | `research.py` |
| B5. 编写算法测试 | 覆盖五种方法、三类约束联合可行/不可行、零换手、现金、退出持仓、Solver 失败及旧接口回归 | `test_sdk_research.py` |

**开发顺序：** 先完成约束计算函数，再接入分组约束、基准偏离约束和风险预算约束，最后测试五种方法的组合情况与求解稳定性。

**交付成果：** `constraint_math.py`、升级后的 `optimize_portfolio(...)`、结构化求解诊断及算法测试。

**完成标准：** 所有成功权重满足声明的硬约束；无法生成有效组合时，返回明确的错误类型、约束信息和求解器诊断。

### 成员 C：核心验证与系统集成

**目标：将新约束接入策略执行流程，完成交易前复核、违规拦截及结果展示。**

| 任务 | 具体工作 | 主要文件 |
| --- | --- | --- |
| C1. 扩展决策对象 | 为 `PortfolioDecision` 增加约束及数据版本证据，更新序列化、反序列化与字节限制 | `sdk/v1/model.py` |
| C2. 实现目标权重验证 | 建立 `verify_portfolio_constraints(...)`，使用 B 的计算函数重新检查传入权重，并接入 `_validate_decision` | 新建 `strategy/portfolio_constraints.py`、`strategy/sdk_runtime.py` |
| C3. 实现计划权重复核 | 在流动性、现金和交易成本调整后检查计划权重，违规时拦截记账 | `strategy/engine.py` |
| C4. 接入诊断结果 | 将 `ConstraintCheck` 写入运行结果，通过 API 提供给风险服务和策略工作台，统一展示限制值、实际值与错误原因 | `apps/api/services/`、相关前端 |
| C5. 完成集成测试 | 覆盖目标权重违规、执行调整后违规、现金和退出持仓、记账拦截及 API/界面数据一致性 | `test_sdk_v1.py`、API/前端测试 |

**交付成果：** 核心约束验证器、交易前两阶段检查、违规拦截及 API/界面集成测试。

**完成标准：** 目标权重和执行计划均通过实际约束检查；违规计划被拦截，检查结果能够完整传递至界面。

### 关键接口交接

| 交接 | 提供内容 | 接收方 |
| --- | --- | --- |
| A → B | 标准化约束规则、行业和基准数据 | 优化器 |
| A → C | 相同的约束规则、数据及版本证据 | 核心验证 |
| B → C | 目标权重、求解诊断、公共约束计算函数 | 核心与执行流程 |
| C → API/界面 | 约束检查结果、执行状态及失败原因 | 风险服务、策略工作台 |

每项功能由对应成员维护一份实现。B 的公共数学函数同时服务于优化后检查和 C 的交易前复核；两次检查分别使用各自业务阶段的实际权重。

## 五、开发顺序与完成标准

### 1. 开发安排

**第一阶段：统一接口**

三人使用一个包含三只股票、行业、基准权重、当前持仓和现金的 fixture，共同确定数据字段、计算口径、容差与诊断格式，由 A 固化公共接口。

**第二阶段：并行开发**

- A：完成约束对象、输入校验和数据适配器。
- B：使用共同 fixture 开发数学计算和优化求解。
- C：使用共同 fixture 开发决策对象扩展、核心验证及集成框架。

**第三阶段：合并联调**

按 A → B → C 的顺序合并。B 接入正式约束对象，C 接入统一数学函数与优化结果，完成端到端测试。

**第四阶段：共同验收**

A 负责数据与版本正确性，B 负责优化结果和 Solver 诊断，C 负责执行拦截及系统展示。三人共同确认全部验收测试通过。

### 2. 最终验收标准

| 验收项目 | 通过条件 | 负责人 |
| --- | --- | --- |
| 约束与数据 | 三类约束可配置；输入合法、时点正确、版本可追溯 | A |
| 组合优化 | 五种方法按支持规则求解；成功权重满足全部硬约束 | B |
| 失败诊断 | 数据错误、约束不可行、协方差问题和 Solver 失败可区分 | A / B |
| 交易前验证 | 目标及计划权重均经过检查，违规计划被拦截 | C |
| 系统集成 | SDK、事件引擎、API 与界面诊断一致 | C |
| 回归测试 | 原有优化方法、现金与换手率核算及事件驱动流程正常 | 各模块负责人 |

### 3. 开发基线与依赖

以 dev3 提交 `d0ce50c` 和 PR #5 为开发基线，继续使用现有 SDK 和事件驱动回测路径。

- **Issue #14：** 数据质量检查、PIT 审计及针对性缺口修复。
- **Issue #15：** 数据快照、代码与环境版本的可复现性管理。

A 负责约束数据接口与这两项已有交付成果的对接；依赖完成前，可先通过保留日期与版本信息的适配器开展开发。正式交付需完成相关依赖集成。

公共文档 `docs/02_STRATEGY_SDK_V1_CONTRACT.md` 按模块维护：A 编写约束对象与数据口径，B 编写优化接口与求解错误，C 编写执行验证和结果传递。

**最终成果：实现行业、基准偏离和风险预算约束的完整链路，覆盖数据输入、组合优化、结果验证、交易前风控和诊断展示。**
